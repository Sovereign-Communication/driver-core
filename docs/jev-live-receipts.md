## 1. Decision tier — real call, verbatim answer shape

State submitted: `{"window_title":"report - editor","foreground_app":"editor","error_dialog_present":false}`

**Question set actually sent** (3 questions, generated by `build_questions`):

| key | type | options |
|---|---|---|
| `action` | `choice` | **14** — every declared vocabulary action |
| `state_is_stable` | `noul` | — |
| `a_blocking_choice_is_required` | `noul` | — |

**Raw response** (`usage: {input_tokens: 829, output_tokens: 172}`):

```
action.choice        = "no_action"      action.confidence = 0.62
action.probabilities = no_action 0.65 | observe 0.26 | read_dom 0.06
                       focus 0.01 | type_text 0.01 | write_file 0.01
                       scroll/call_read_tool/click/run_probe/press_key/
                       read_value/submit_irreversible/delete_file 0.00
                       sum = 1.000000
state_is_stable                -> {"type":"noul","noul":0.81}
a_blocking_choice_is_required  -> {"type":"noul","noul":0.08}
```

Three facts worth keeping:

1. **`confidence` ≠ `probabilities[choice]`.** `0.62` vs `0.65`.
   `validate_answers` prefers the explicit `confidence` and falls back to the
   distribution — and on live data the fallback would have been *wrong*.
2. **A `noul` answer carries exactly two keys**, `type` and `noul`. No
   `confidence`, no `probabilities`. Confirms the README's claim that Noul is
   P(yes) and nothing more.
3. **No undeclared answers came back.** The all-or-nothing contract held
   against the real provider, not just a fake.

## 2. Calibration — five identical calls, real transport

| run | status | action | confidence | `state_is_stable` | `blocking` | cost |
|---|---|---|---|---|---|---|
| 0 | native | `no_action` | 0.6400 | 0.82 | 0.08 | $0.000034818 |
| 1 | native | `no_action` | 0.6500 | 0.81 | 0.08 | $0.000034818 |
| 2 | native | `no_action` | 0.6300 | 0.81 | 0.08 | $0.000034818 |
| 3 | native | `no_action` | 0.6500 | 0.82 | 0.08 | $0.000034818 |
| 4 | native | `no_action` | 0.6700 | 0.81 | 0.08 | $0.000034818 |

**Budget settled `$0.000174090` — exactly 5 × $0.000034818. Reserved `$0.000000`.**
Five audit records written, kind `decision`, metadata-only fields, no state.

### What this says, and it is a design warning

* **The action is perfectly stable.** `no_action` five times out of five.
  The *ranking* is reliable.
* **The number is not.** Choice confidence spans 0.63–0.67 (±0.02) on an
  identical input. Token counts were identical every run (829/172), so this is
  sampling variance, not a different prompt.
* **Therefore a threshold placed inside that band flaps.** At 0.65 this exact
  state acts on runs 1 and 3 and escalates on runs 0, 2 and 4. That is not a
  marginal case — it is the *measured* behaviour of this threshold on this state.

`DRIVER_CONFIDENCE_THRESHOLD` sits at **0.70**, safely above the whole observed
band, so today's default is not exposed. But the gap between 0.67 and 0.70 is
0.03, and the jitter is 0.04. **The default clears the observed band by less
than the model's own run-to-run variance.** That is the finding: it should be
widened, not documented.

This is what `JEV-SEM-calibration` needs, and it is now grounded in a receipt
rather than a proposal.

## 4. Vision tier — two real defects, found by running it

`DRIVER_SCREEN=1` with `DRIVER_SCREEN_OUT` set produced a **real 44,551-byte
PNG**. Two independent vision extractors ran and both were billed.

```
capture   : ok=True source=screen fingerprint=5efb669930e64738
seq=1 extraction tier=vision ok=False cost=2.1546e-05 usage_source=actual
         reason="model returned no parseable state"  (vision-0)
seq=2 extraction tier=vision ok=False cost=2.1546e-05 usage_source=actual
         reason="model returned no parseable state"  (vision-1)
seq=4 refusal reason=insufficient_agreement
         detail="0 of 2 slots answered; quorum is 2."
cost_usd : 4.3092e-05
```

**The gate behaved perfectly.** Two extractors disagreed-by-absence, quorum was
not met, the step stopped at `agreement`, and **the decision model was never
called**. Billed calls that produced nothing were still charged. This is the
design's central claim, observed live.

### Why the extraction could not succeed — two independent reasons

*(Corrected 2026-10-05. This heading originally read "But the extraction
cannot succeed, for two independent reasons", which was true of the code as
shipped and stopped being true of the code as it now stands. Both defects are
repaired; §4a carries the repair and the receipt. What follows is kept because
it is the evidence the repair was built from.)*

**Defect A — the capture is a local path sent to a remote endpoint.**
`_capture_state` emits `{"image_ref": "C:\\...\\probe_capture.png"}`. The
endpoint is `https://api.typesafe.ai/v1/systemone`, a remote HTTP service with
no access to this machine's filesystem. Raw live answer:

```
answers.observation.choice = "unreadable"   (needs "observed")
probabilities              = {observed: 0.05, unreadable: 0.95}
confidence                 = 0.90
payload["state"] present   = False
payload["fields"] present  = False
```

Jev was **right**. Given an unresolvable string it correctly declined. The
docstring says the capture is "a path, a base64 payload or a handle" — but only
one of those three is something a remote vision model can read. **The vision
tier has never been able to work as shipped**, and no hermetic test can catch
it, because the fake transport never resolves the path either.

**Defect B — nothing asks for the fields.**
`_state_from_payload` looks for `payload["state"]` or `payload["fields"]`.
The extraction pack asks exactly **one** question: `observation`, a `choice`
between `observed` and `unreadable`. **No question elicits a field value**, so
the parser is looking for keys the model was never asked to produce. Both keys
were absent in the live payload. Even with a readable image, this parse cannot
succeed.

So `DRV-2`'s vision sub-item is not "wire a provider."

**It is also not "inline the image as base64."** This paragraph originally
recommended exactly that, and **that recommendation was wrong** — it was
written from the assumption that the endpoint decodes images, which it does
not. §4a disproves it against the live service. Base64 is tokenized as text:
253 KB and 102 KB payloads are rejected outright with `max_tokens_exceeded`,
and an 8 KB JPEG is accepted only to consume 8,129 input tokens and answer
"is this a screen?" at 0.11. **Do not re-encode a screenshot; it was tried.**

The sub-item is: **describe the screen as text and ask questions about the
description**, plus one typed question per field the model can answer in a
closed vocabulary. That is what shipped.

### 4a. Both defects are FIXED — and the premise underneath them was wrong

#### CANONICAL CONSTRAINT: Jev is text-only. Images cannot reach it.

> **Never propose re-encoding a screenshot for Jev.** It was tried against the
> live endpoint and it cannot work. Any plan that proposes base64, a data URL,
> or "just send the PNG" must be **redirected, not attempted** — to describing
> the screen as text (`osal.describe_screen()`) and asking typed questions
> about that description.
>
> The receipt is the token count. Probing with progressively smaller encodings:

| payload | result |
|---|---|
| `image_ref` = local path | HTTP 200, `unreadable` @ 0.93 |
| base64 PNG, 253 KB | HTTP 400 `max_tokens_exceeded` |
| base64 JPEG 102 KB, as data URL | HTTP 400 `max_tokens_exceeded` |
| base64 JPEG 8 KB, as data URL | **HTTP 200** -- but `is this a screen?` = **0.11**, `title bar visible?` = **0.03** |
| base64 2x2 PNG (76 bytes) | HTTP 200, `unreadable` @ 0.45, near-uniform |
| **plain text control** | `unreadable` @ 0.50 |

The small JPEG was *accepted* and consumed **8,129 input tokens for 11,183
characters of base64** -- the token count tracks the base64 length, which is
the signature of text tokenization, not image decoding. TypeSafe's own
documentation is blunter: **"Jev currently accepts text only."**

**Jev cannot see images.** Both "defects" were symptoms of that one fact.

The fix therefore removes pixels from the path rather than re-encoding them.
`osal.describe_screen()` reads the foreground window through the window manager
(Win32 via `ctypes`): title, application name, window class. It is exact where
a transcription of a picture would be a guess, free, and stdlib-only. The
extractor asks one typed question per field the model can answer in a closed
vocabulary -- `boolean` -> `noul`, `enum` -> `choice` over the declared values
plus an explicit `<absent>` -- and code supplies the free-text facts the model
could only invent. That is the project's own rule applied inside the one tier
that used to be the exception: structured input before pixels.

**Proof through the real surface**, real server, genuine capture, `jev-1.13.0`:

```
capture   : ok=True source=screen fingerprint=3608f1cdd6d63d4d
seq=1 extraction tier=vision ok=True  cost=2.5872e-05 usage_source=actual  (vision-0)
seq=2 extraction tier=vision ok=True  cost=2.5872e-05 usage_source=actual  (vision-1)
agreement: outcome=agreed asked=2 answering=2
   window_title         agreed=True 2/2
   foreground_app       agreed=True 2/2
   error_dialog_present agreed=True 2/2
decision : native=True conf=0.70 model=jev-1.13.0 cost=3.486e-05
result   : no_action_recommended
```

Before the fix the same step produced two slots with `ok: False`
("model returned no parseable state") and `insufficient_agreement`. After it,
**both slots answer and the tally genuinely cross-verifies.** Extraction spend
$0.000051744 over two slots, decision $0.00003486, all at $0.042/Mtok.

A third bug surfaced while fixing: `_capture_state` received the `Capture`
object and emitted `{"image_ref": str(capture)}`, discarding the encoded
payload entirely -- the model was never sent a path, only `repr()` of an object.

#### What the repair actually is

`osal.describe_screen()` reads the foreground window through the window manager
(Win32 via `ctypes`): title, application name, window class. Exact where a
transcription of a picture would be a guess, free, stdlib-only, and it lives in
`osal` because the package's AST guard confines OS contact to that one module.

The extraction pack is now **generated from the schema** the state is validated
against: `boolean` -> `noul`, `enum` -> `choice` over the declared values plus
an explicit `<absent>`. Free-text fields are deliberately not asked for, because
a `choice` cannot return a window title and a model asked to invent one would
be fabricating a fact the platform already holds exactly. That is the project's
own rule — *counting, arithmetic, paths and gates stay in code; Jev owns bounded
judgment* — applied inside the one tier that used to be the exception.

### A.4 FINDING — a documented guarantee the endpoint cannot keep

The endpoint's own `Choice` documentation states, verbatim:

> `probabilities`: The full probability distribution across every option.
> **The sum of all values is 1.**

and publishes every one of its seven worked examples quantised to **two
decimal places** (`0.04 + 0.35 + 0.61 = 1.00`).

At eleven options those two documented facts stop being simultaneously
satisfiable. Measured live against the real endpoint, asking the action
question with eleven options offered:

| run | scored | rejected by the shipping bound | deviations from 1 |
|---|---|---|---|
| first | 20 | 9 | `0.00` × 11, `-0.01` × 9 |
| second | 16 | 7 | `0.00` × 9, `-0.01` × 7 |

Every entry was on a hundredth (decimal places seen across 176 entries: `0` ×
96, `2` × 74, `1` × 6). One rejected distribution, verbatim:

```
click 0.03 | delete_file 0.0 | focus 0.01 | no_action 0.79 | observe 0.14
press_key 0.0 | read_value 0.02 | scroll 0.0 | submit_irreversible 0.0
type_text 0.0 | write_file 0.0            sum = 0.99
```

The consequence was not a refusal. `Decision.usable` gates the step, so a
`malformed` envelope escalates and **nothing acts** — while the thrown-away
answer named `no_action` at 0.77–0.80 confidence in **7 of 7** rejected cases,
and **7 of 7** still contained their own chosen option. A three-option build
never deviated in any observed call: the failure is a function of option count.

The check was enforcing a real guarantee. It was enforcing it with a fixed
`1e-3` bound, which the endpoint's own printing precision cannot satisfy.

### A.5 The decision, put to Jev three times

`ask_until_grounded`, gate `0.99`, iterated with strictly more context each
time. Its confidence in its own answer *fell* as the context grew:

| iteration | context supplied | answer | confidence | dominant driver |
|---|---|---|---|---|
| 1 | the check, the contract, the invariants, the alternatives | `keep_rejecting` | **0.95** | `keep_contract_intact` 0.34 |
| 2 | + the downstream consequence (a rejection means nothing acts) and the live receipts | `keep_rejecting` | **0.19** | `keep_contract_intact` 0.48 |
| 3 | + the endpoint's own published contract and worked examples | `keep_rejecting` | **0.34** (mass 0.47 vs `bound_from_precision` 0.42) | `keep_contract_intact` 0.43, `fidelity` 0.28 |

Iteration 3 also asked the arithmetically decidable sub-question — *can both
documented facts hold at once at eleven options?* — and got `noul = 0.67`.
That is honest calibration, not a knowledge gap: a prose choice between two
invariants the tree genuinely holds has no ground truth in the evidence, so
the model will not manufacture 0.99 for it.

**The driving decision was therefore put to the operator**, with the evidence
above. The operator chose **bound by the endpoint's own precision**.

### A.6 The repair — a bound derived from the endpoint's own precision

`validate_answers` no longer compares the sum against a literal `1e-3`. The
accepted deviation is derived, per response, from the precision the endpoint
actually emitted:

```
unit      = 10 ** -inferred_grid(probabilities)
tolerance = min(max(FLOAT_NOISE_TOLERANCE, len(probabilities) * unit / 2),
                MAX_ACCEPTED_DEVIATION)
```

* `inferred_grid` reads the last decimal place off the emitted entries,
  floored at one decimal place so a set of whole numbers cannot imply that the
  units place is a hundredth.
* `FLOAT_NOISE_TOLERANCE` is `1e-9`: 255 entries of at most 1.0 cannot
  accumulate more than a few parts in 10^-14 of double error, and a
  full-precision distribution gets essentially nothing else, because full
  precision means the sum is meant to be exactly 1.
* `MAX_ACCEPTED_DEVIATION` is `0.1`: beyond one part in ten a distribution is
  describing a different question, whatever grid it arrived on.

For the observed case — eleven options, every entry on a hundredth — the
tolerance is `11 × 0.005 = 0.055`, and the measured `-0.01` is accepted.

**The rule is unchanged; only the bound moved with the precision.** The
existing pinned test (a distribution summing to 1.8) is still refused, by both
the grid rule and the ceiling. The deviation is now recorded rather than
silently absorbed: `Decision.probability_deviation` appears in `to_dict()` and
in the `decision` audit record, so a decision acted on after a tolerated
deviation says so in the log. It is `0.0` when the sum was exact.

Two consequences worth naming:

* the recorded chain `tests/test_audit_compat.py:GOLDEN_CHAIN` was regenerated
  through the documented paste-over helper, because the `decision` record
  gained one metadata field;
* `RECORDED_CHAIN` was **not** touched and still re-hashes clean, which is the
  whole point of it: a log written under the superseded price and without the
  new field still verifies.

### A.8 R7 — a round budget that ran out read as a settled answer

Found by reading `ask_until_grounded` while a full audit was in flight. It is
the most consequential defect of this pass because it was **silent**.

The loop had three declared ways to end unsettled. A fourth existed and had no
name: a model still asking for *new* context when `max_rounds` ran out fell
through the bottom of the `for` and was returned with `ungrounded=False` — a
**settled** answer for a question that never settled — and `aggregate` then
counted it among the grounded.

Measured against the superseded checkpoint (`build/jev_audit/pre-r7.jsonl`,
403 records, retained as evidence rather than deleted):

| | |
|---|---|
| records reported `ungrounded=False` after consuming all three rounds | 19 |
| share of that checkpoint | 4.7% |
| derivable check | every one of them had `grounding.supplied` in round 3 |

The derivation is exact, not heuristic: the loop supplies a bucket in the round
it breaks, so a supply recorded in the *final* round is a loop that had no
round left to ask in. That is what let the impact be quantified from a
checkpoint that was already paid for instead of guessed at.

The repair adds a fourth `reason_kind`, `rounds_exhausted`, and the report now
separates four conditions rather than averaging them into one count:

| kind | what it means | what it asks of the reader |
|---|---|---|
| `transport` | the call never completed | retry, or fix the connection |
| `unanswerable` | the model named a kind of context no supplier has | go and obtain that material |
| `still_short` | every bucket was supplied and an answer is still below the gate | accept it — the question has no confident answer from this evidence |
| `rounds_exhausted` | still asking for new context when the round budget ran out | raise `max_rounds`, or spend the budget again |

Guarded hermetically in `tests/test_jev_audit.py`, and red-checked:

* `RoundBudgetTests.test_exhausting_the_round_budget_is_reported_ungrounded`

* `...test_settling_on_the_last_permitted_round_is_not_exhaustion` — the
  discriminator. A loop that settles on its final permitted round has the same
  `rounds == max_rounds` and must stay **green**; that is why the rule derives
  from `grounding.supplied` and not from a round count.
